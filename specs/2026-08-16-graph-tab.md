# Design spec — a "graph" Herdr tab for Atomic's workflow graph

> **Status: BLOCKED at Phase 0. Core mechanism disproven, live-tested 2026-08-16.**
> Cross-process `/workflow connect <run-id>` does not work: a second `atomic` process in the
> same project directory returned `Error: Run not found` for a run launched and completed in
> a different process's session, even though the run completed successfully
> (`/workflow status <run-id>` succeeded in the original process). Runs are scoped to the
> launching session, not discoverable project-wide. §3's approach as written does not work.
> See §4 for what actually works.
> No prior request for this exists in the repo (checked `research/`, `build/`, `specs/`, git
> log) — this is a fresh design, not the earlier, unrelated
> `research/mission2-graphview-2026-08-15.md` doc-wording fix.

## 1. Ground truth (checked against installed Atomic `0.9.13`)

- Atomic already ships a live graph view. It is a **TUI overlay inside an interactive Atomic
  session**, opened by `/workflow connect <run-id>`, `F2`, or automatically via
  `autoAttach: true` on launch. Source: `atomic/docs/workflows.md:116, 2977, 3176, 3181`.
- There is **no standalone CLI subcommand** that renders or exports the graph
  (`atomic --help` lists only `install/remove/update/list/config/auth`; no `atomic workflow`
  top-level command). The graph only exists inside a running Atomic session's TUI.
- Durable/named workflow runs are described as "resumable across sessions"
  (`atomic/docs/workflows.md:341`). **Live-tested and disproven**: launched a real
  `classify-and-act` run (runId `679f494d-e3b0-4650-b794-1f632d9fb12f`) from this session,
  let it complete, then opened a second, separate `atomic --no-session` process in a fresh
  Herdr pane (same project cwd) and sent `/workflow connect 679f494d-...`. Result:
  `Error: Run not found`. Meanwhile `/workflow status <run-id>` succeeded in the
  *original* process. "Resumable across sessions" means a given session surviving its own
  process restart (what `--resume`/`--continue` do), not a run being visible to an
  unrelated second process in the same directory.
- Precedent in this repo: `kanban` and `team` Herdr tabs (`scripts/kanban.sh`,
  `scripts/team-status.sh`) are **custom pollers reading files under `build/`**, not Atomic
  itself. That pattern does not transfer here — there is no file-based export of graph
  state; the graph only exists inside Atomic's own TUI. So a "graph" tab must run `atomic`
  itself, not a lightweight shell poller.

## 2. Goal

A Herdr tab labeled `graph`, opened the same idempotent/best-effort-but-visible way as
`kanban`/`team`/`team-chat` (see `build.sh`'s `_open_side_tab` helper), that shows the live
stage graph of the mission's active named workflow run — without the human hunting for a
run id or typing `/workflow connect` by hand.

## 3. Recommended approach

Spawn a small, separate `atomic` process in the new pane, in the same project directory, and
drive it to `/workflow connect <run-id>` — literally reusing Atomic's own overlay, not
reimplementing it.

```
herdr tab create --label graph --cwd "$HERE" --no-focus
herdr pane run <pane-id> atomic --no-session   # bare session, same project dir
herdr pane send-keys <pane-id> "/workflow connect <run-id>" Enter
```

Open question this raises: **which run-id?** Two sub-options:

- **3a — targeted:** the lead passes a specific run-id at the moment it launches a named
  workflow (e.g. from inside `feature-development` or a custom workflow run started via
  `workflow({action:"run"...})`). Works cleanly, but only fires when the *lead itself* is
  the one launching a tracked named-workflow run — not for ad hoc subagent/intercom work,
  which is most of how this team currently operates.
- **3b — picker:** open the pane with a bare `atomic` session and send `/workflow status`
  (no run-id) or leave the human to pick from the `/workflow connect` run picker
  (`atomic/docs/workflows.md:132`, "shows five runs at a time"). Lower automation, but works
  regardless of who launched the run, and needs no run-id plumbing through intercom.

**§3 is disproven as written (see §1's live test). Do not extend it further.**
See §4 for the only mechanism confirmed to work.

## 4. What actually works — fallback approach

The only place `/workflow connect <run-id>` is confirmed to work is **inside the exact
session that launched the run**. So a "graph" tab cannot be an independent `atomic` process
— it must be a view into an *existing* agent's live session.

Options, in order of how much they fight Herdr's pane model:

- **7a — focus shortcut, not a new process.** `scripts/graph-tab.sh` becomes a thin wrapper
  around `herdr pane focus <lead-pane-id>` (or `herdr agent prompt <lead> "/workflow connect
  <run-id>"` if the lead is mid-turn and can accept a steer). This does not create a
  dedicated `graph` tab with its own pane — it jumps the human to whichever pane actually
  owns the run. Cheap, truthful, but not a persistent side-tab like `kanban`/`team`.
- **7b — ask upstream.** File the cross-session attach gap as a real Atomic feature request
  (a `--attach-session <id>` style flag, or a documented API/RPC to query run graph state
  headlessly) rather than working around it. This is the only path to a *true* independent
  `graph` tab matching `kanban`/`team`'s pattern.
- **7c — do not build.** Given this team's actual usage is ad hoc subagent/intercom
  delegation, not top-level named-workflow launches, a dedicated graph tab may not earn its
  keep even if 7b ships. Revisit only if a mission starts launching named workflows
  routinely.

**Recommendation:** do not build on §3. If a graph surface is still wanted, build 7a first
(near-zero cost, uses only existing `herdr pane focus`) and treat 7b as a separate,
longer-lead request to file upstream, not something this repo can build around today.
